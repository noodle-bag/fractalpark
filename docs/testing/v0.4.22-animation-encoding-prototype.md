# v0.4.22 Animation Encoding Prototype

- Status: Slice 0b implementation evidence
- Scope: fixed-step timing, MP4/WebM capability probing, dependency budget,
  backpressure, cancellation, and reference-profile encoding
- Product activation: none

## Boundary

This prototype evaluates the animation route required before production Export
Jobs are implemented. Code under `src/prototypes/` is test-only and has no
production importer. It does not add Export UI, persist animation speed, change
the renderer, or enable MP4/WebM in the product.

The approved product inputs represented here are MP4 and WebM, the nine
`0.25x-4x` speed values, fixed output timestamps mapped to canonical animation
time, the default `1920x1080 / 60 FPS` profile, and the maximum
`3840x2160 / 60 FPS` profile. Confirmed settings never silently fall back to a
different size or frame rate.

## Candidate route

The prototype prefers browser WebCodecs through Mediabunny `1.59.1`, using its
MP4/WebM muxers and `CanvasSource`. Frames are supplied with explicit timestamps
and awaited one at a time, which gives the encoder and muxer backpressure. MP4
prefers AVC and WebM prefers VP9/VP8; every exact width, height, frame-rate, and
bitrate combination is probed before encoding.

Mediabunny is an MPL-2.0 development dependency in this prototype. A narrow
bridge dynamically imports only the MP4/WebM writing symbols, and no production
module imports the prototype. The browser probe records the tree-shaken raw/gzip
bundle size separately from the package's installed size. Production adoption
still requires license notice review and a measured product build before the
dependency moves to a runtime dependency.

## Time, memory, and cancellation

- `effectiveDuration = baseDuration / speed`.
- Output timestamps advance by the chosen FPS; canonical sample time is
  `outputTime * speed`.
- A fractional final frame is shortened so the declared media duration remains
  exact instead of silently changing FPS or animation speed.
- The budget helper exposes a named three-frame RGBA planning budget and
  bitrate-based output estimates. Sequential awaits avoid an app-owned frame
  queue; codec/library internal memory remains unmeasured.
- An `AbortSignal` can cancel module waiting or an active encode. A canceled
  consumer does not start encoding if the shared module load resolves later;
  active cancellation calls the output's resource-release path. Concurrent
  module requests are deduplicated, while a rejected load clears the cache so a
  later explicit retry can make a new request.

## Validation matrix

`playwright.animation-prototype.config.ts` defines Chromium, Firefox, and WebKit
projects. Each available engine must attach:

1. exact 1080p60 and 4K60 capability results for MP4 and WebM;
2. dependency bundle bytes and probe timing;
3. playable MP4/WebM metadata from deterministic fixed-step samples;
4. one-second reference encodes at 1080p60 and 4K60, including elapsed time,
   output bytes, dimensions, duration, codec, and optional JS heap readings.

Playwright WebKit is not equivalent to Safari on Apple hardware. Safari and at
least one physical mobile device remain release-level evidence. Any unavailable
engine/profile/container combination is an explicit capability failure; it must
not be reported as a pass or replaced with a lower frame rate or resolution.

## Local Chromium evidence (2026-09-25)

Playwright Chromium 145 on Linux passed all three isolated browser tests from a
secure localhost origin. WebCodecs was available on the main thread and in a
Dedicated Worker. Exact capability probes selected AVC for MP4 and VP9 for
WebM at both reference profiles; MP4 also reported AV1, while WebM reported
VP8 and AV1 as additional encodable candidates.

The narrow MP4/WebM bridge produced a minified browser probe bundle of
`223,308 B` raw / `59,851 B` gzip. The first codec probe, including dynamic
module preparation, took about `1.33 s`; cached follow-up probes took roughly
`44-118 ms`. This is prototype evidence, not a production chunk budget or a
claim about network latency.

| Route | Frames | Output | Encode time | Decoded result |
|---|---:|---:|---:|---|
| MP4 / AVC, 1920x1080@60 | 60 | 1,462,114 B | 1.207 s | 1920x1080, 1.000 s |
| WebM / VP9, 1920x1080@60 | 60 | 935,653 B | 1.188 s | 1920x1080, 1.000 s |
| MP4 / AVC, 3840x2160@60 | 60 | 4,946,186 B | 4.035 s | 3840x2160, 1.000 s |
| WebM / VP9, 3840x2160@60 | 60 | 3,149,243 B | 3.644 s | 3840x2160, 1.000 s |

An active WebM job aborted after frame 4 with `AbortError`; a subsequent
Dedicated Worker job encoded 15 fixed-step VP9 frames into a playable 0.5 s
WebM. The browser exposed only coarse constant JS heap readings, so those values
are not accepted as memory evidence; the explicit queue budget remains the
current memory bound until a real-device profiler is used.

Firefox and WebKit binaries are not installed on this machine. Their downloads
were already blocked by the current proxy during Slice 0a, so the unchanged
environment failure was not retried. Safari on Apple hardware and physical
mobile remain unmeasured. These are named validation gaps, not passes.
